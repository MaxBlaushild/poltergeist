# Travel calendar setup

Travel Angels includes an ongoing personal calendar, individual trip permissions, guest browsing and email verification, invitation claiming, trip hosts, participation requests, guest subscriptions, and email broadcasts. Each calendar stop opens a trip page with a cover image, attendance, lodging, and flights.

**Phone input and test-account sign-in.** Sign-in and shared-trip account claiming share a searchable country-code picker. It starts from a supported device-locale region, falling back visibly to US, and accepts national numbers or pasted full `+` international numbers. Pasted international numbers update the selected country; country-aware parsing handles national trunk prefixes and preserves significant leading zeros. Only validated canonical international numbers reach the authentication service. Country selection uses bundled metadata; it does not request location access or query an external service.

Web and native clients recognize the authenticator's allowlisted test accounts in both flows. They skip requesting an SMS and ask for the configured six-digit test code instead. Login still goes through the server and requires a successful authentication response; the client does not embed or prefill that code. Keep `lib/utils/auth_phone_number.dart` aligned with `go/authenticator/cmd/server/test_auth_users.go` when changing the allowlist.

**Database.** Apply the normal repository migration workflow to the intended environment before starting the updated API. Migration `000473_travel_calendars` adds the calendar, stop, access, collaboration, and participation tables. Migration `000474_travel_calendar_guests` adds verified recipient identities, invitation/subscription records, and the notification outbox. Migration `000475_travel_trip_pages` adds host roles, capacity and roster settings, reserved places, revision checks, an audit log, and protected trip media. The server does not automatically modify the schema. Both up and down migrations are included; rolling down removes feature data.

**API configuration.** The same calendar routes are registered in the standalone Travel Angels service and the aggregated core API. Configure the process running those routes:

| Variable | Purpose |
| --- | --- |
| `TRAVEL_ANGELS_WEB_URL` | Public HTTP(S) address of the hosted Flutter app, without a fragment. Used for calendar, stop, and preference links. |
| `TRAVEL_ANGELS_EMAIL_FROM` | Verified email sender address; falls back to `EMAIL_FROM_ADDRESS`. |
| `TWILIO_ACCOUNT_SID` | Account used by the existing email client. |
| `TWILIO_AUTH_TOKEN` | Credential used by the existing email client. |
| `FLIGHTAWARE_API_KEY` | Optional FlightAware AeroAPI key for flight-number/date and airport-route/date lookup. Keep it on the API server, never in Flutter build defines. |

Missing mail configuration produces an actionable unavailable response for verification/invitation/broadcast actions rather than reporting an email as sent. Calendar creation and permission-controlled link browsing remain available. The shared email client accepts an injected HTTP client; Travel Angels sets a 30-second request timeout.

Configured API processes drain the durable notification outbox every 10 seconds. Deliveries are rechecked against current stop permissions and subscriptions before sending. Known failed deliveries can be retried through the UI. A delivery with an uncertain provider result remains in `sending` for review, because blindly resending could duplicate a message. Successful deliveries are not automatically resent.

**Public web hosting.** The canonical origin is [https://travel-angels.org](https://travel-angels.org), with `https://www.travel-angels.org` as an alternate address and API origin `https://api.unclaimedstreets.com`. Both web names use the existing private S3 bucket `travel-angels-web-872408892710` and CloudFront distribution `E2EQ9RE874X8K6`. The original [CloudFront address](https://d3hd0wcyslgumm.cloudfront.net) remains the fallback. Both custom domains passed public DNS and HTTPS checks on October 28, 2026. Verify registration/delegation, certificate issuance, CloudFront deployment, and HTTPS before any future domain cutover. Existing hosted-zone NS/SOA records and registrar name servers are preserved. Keep the ACM DNS-validation CNAMEs in place after issuance so automatic certificate renewal continues to work.

Publish the current Flutter app from the repository root with `make travel-angels/web-deploy`, or `FLUTTER_BIN=/Applications/flutter/bin/flutter make travel-angels/web-deploy` when Flutter is not on `PATH`. The command reads the independent `terraform/travel-angels-web` outputs, including `website_url` for the canonical web origin; `cloudfront_url` retains the fallback. It builds with the API and canonical web URLs, uploads assets, and requests a CloudFront invalidation. Publish again after the domain outputs change, then verify the distribution, invalidation, `release.json`, and browser UI. Provisioning hosting does not by itself verify that a particular build is live. The initial October 28, 2026 release used the CloudFront address, and its URL-only backend deployment was `sonar_core:51`; the custom-domain rollout completed in `sonar_core:52` with the new canonical origin.

Hosting has its own local `terraform/travel-angels-web/terraform.tfstate`. Use `terraform -chdir=terraform/travel-angels-web init`, `plan -out=hosting.tfplan`, and `apply hosting.tfplan` only for reviewed hosting changes, and retain a secure backup of that state. Ordinary web releases do not require a Terraform apply. Do not apply the unrelated parent Terraform root to upload the web app. Full commands and recovery notes are in [the deployment guide](../../../deploy/travel-angels/README.md).

**Web and mobile build configuration.** The deployment command supplies the live API origin explicitly. For a direct build, set both URLs:

```sh
flutter build web \
  --dart-define=TRAVEL_ANGELS_API_URL=https://api.unclaimedstreets.com \
  --dart-define=TRAVEL_ANGELS_WEB_URL=https://travel-angels.org
```

The web URL can be inferred from the browser origin for browser-created links; provide the build define for native app sharing. The configured backend also returns share URLs. Use the aggregated core API for split-origin development: its CORS policy accepts `X-Travel-Guest-Token` alongside account authorization. Standalone Travel Angels retains its existing same-origin/CORS behavior.

After DNS and HTTPS are verified for the custom domain, update the live API's generated links without changing application images: first run `python3 deploy/travel-angels/configure_web_url.py --web-url https://travel-angels.org` from the repository root and review the dry run; rerun with `--apply` to register the URL-only task revision and start the ECS rollout. Use a current AWS CLI (or the script's `--aws-cli` option with a durable executable path); outdated ECS models are rejected to avoid dropping task fields. The script preserves task configuration, pins all application images to their current running digests, and changes only `core.TRAVEL_ANGELS_WEB_URL`. Monitor rollout completion afterward. The parent Terraform variable in `terraform/travel_angels_web_url.tf` records the desired canonical origin for future reviewed infrastructure applies; it does not change the live runtime by itself and is not a reason to apply the parent root during a web release.

Shared URLs use fragments, so ordinary static hosting does not need a separate rewrite rule for each calendar:

- `/#/calendar/<share-token>` opens a filtered calendar.
- `/#/stops/<share-token>` opens its authorized trip page directly.
- `/#/preferences/<management-token>` manages notifications without an app account.

Path-based and `travelangels://` equivalents are also understood by the app. Shared calendar and stop routes bypass the ordinary account login gate. Restricted recipients verify their email for limited guest access. Joining then uses the existing phone-based account login/registration and explicitly associates the verified invitation; the UI returns to review instead of submitting automatically.

**Calendar behavior.** New calendars are private. Trips inherit the owning calendar's audience unless set to private, specific people, or anyone with the link. Trip overrides replace the calendar audience. Displaying a hosted trip on another calendar preserves its owning policy. Calendar editors retain their existing rights on legacy stops; newly created trips use explicit, accepted full-host roles. Only a calendar's owner can create new trips in it.

**Trip hosts and attendance.** New trips list their creator as an attending host. Hosts can edit and publish content, manage the audience, approve attendance, and invite or remove non-owner hosts. Invited hosts must accept; accepting as an organizer does not reserve a place. Ownership transfer and deletion belong to the owner. Existing stops keep their legacy roles until the owner reviews and confirms conversion; collaborators are never silently upgraded. Attendance limits count distinct confirmed people and places reserved during date reconfirmation. Optional waitlists require manual host approval. Guests can browse authorized details, but must claim an account and explicitly submit their attendance choice. Roster consent is required before sharing a participant's identity with other attendees.

**Trip images and logistics.** Hosts can add, replace, or remove a cover using the trip page's compact cover control. Cover uploads accept JPEG and PNG up to 8 MB and 20 million pixels. The API re-encodes images and strips metadata before using the shared AWS file-storage client. Apply migration `000478_travel_trip_media_storage`, then set `TRAVEL_ANGELS_TRIP_MEDIA_BUCKET` to a private S3 bucket in the existing AWS client's region. The API role needs `s3:PutObject`, `s3:GetObject`, and `s3:DeleteObject` for its `trip-heroes/*` prefix. `terraform/travel_angels_media.tf` provisions an encrypted bucket with all public access blocked; `terraform/ecs.tf` grants the core task role access and supplies the environment variable. No separate AWS credential or storage service is needed. Do not use a public profile-image bucket for trip covers.

Cover URLs remain permission-protected API routes. Reads recheck the current audience, guest credentials, and draft/published attachment after fetching from S3, and responses cannot be publicly cached. A replacement stays private in the draft until publication. Draft removal, publication changes, and trip deletion clean up objects no longer referenced by either version; storage cleanup failures are logged with the object key for operational retry. S3 requests have deadlines and reads are capped at 8 MB. Existing PostgreSQL image bytes remain readable; when the bucket is not configured, local/legacy deployments continue using PostgreSQL. Include both stored objects and the media metadata table in backup planning. To roll back migration 478 after S3 uploads, first restore each referenced object's bytes to `tc_trip_media.data` and clear both storage columns in the same update; the down migration refuses to discard external image references.

Lodging and flight records live in the trip's draft and published content. Their audiences can be narrower than the trip's audience; manually entered exact lodging addresses and arrival instructions use separate restrictions. Host notes remain private to hosts. Publishing content and applying immediate permission changes both check the current trip revision, so a stale editor cannot overwrite a host's newer changes.

**Lodging properties and photos.** Hosts can search Google lodging properties or create a manual stay with an Airbnb/hotel link. Property search uses the existing `GOOGLE_MAPS_API_KEY`; enable Places API (New) for that key and retain its billing/API restrictions. Searches prefer the first ordered draft destination with valid coordinates in the canonical destination catalog, using Google's 50 km location bias without changing the search text. Trip-local labels, client-supplied coordinates, and missing catalog coordinates do not imply a search location; providers without nearby search retain ordinary text search. If property lookup is unavailable, manual lodging and user photo uploads still work. A selected Google property stores only `{provider: "google", placeId: ...}`. Names, addresses, ratings, photo resource names, and attribution metadata are fetched live; the API does not cache or persist those provider details or photos. Use the trip's own lodging name for the saved label. The property card displays Google/source and photo-author attributions returned with live data.

Google property identity and its public address follow the lodging entry's audience. They are intentionally separate from narrower manually entered address/arrival instructions. Host-only search/preview routes live under `/calendar/stops/:id/lodging-properties`; attached metadata and provider photo routes live under `/calendar/stops/:id/lodging/:entryId/property`. Published routes enforce both trip and lodging access. Hosts can request `draft=true`; guests cannot read drafts. Provider and S3 network reads happen outside permission locks, then current guest identity, audience, and attachment are rechecked before responding.

Migration `000479_travel_lodging_media` scopes uploaded media to its lodging entry. Each saved draft lodging accepts up to six JPEG/PNG uploads (8 MB each, same sanitization as covers) through `POST /calendar/stops/:id/lodging/:entryId/photos` with multipart `image`, `altText`, and `revision`. Save a new lodging first; each successful upload returns the updated stop/revision. Selected photo removal is saved through the normal trip draft update. Uploaded photos use the existing private bucket under `trip-lodging/*`; grant the API role the same read/write/delete permissions for that prefix. Draft and published references are retained independently, and deletion/publication cleanup also handles lodging photos. Media cannot be attached to another lodging or used as a trip cover. Migration 479 rollback requires removing lodging photo attachments/media first, so dropping the discriminator cannot broaden access.

**Shared trip documents and comments.** Migration `000481_travel_trip_documents` adds shared attachments and per-document comments, independent of private Library bookmarks and draft publication. The trip page's Documents navigation opens the shared section. Current hosts and confirmed attendees (including reserved places awaiting reconfirmation) can read and contribute while they retain trip access. Guests see an account/join prompt. Cancelled trips remain readable and allow removal, but prevent new attachments and comment creation or editing.

Members can upload original PDF, DOCX, XLSX, CSV, TXT, JPEG, or PNG files up to 20 MiB, add an HTTP(S) source link, or explicitly share a snapshot of a guide they own. Library snapshots exclude personal notes and leave the original guide's audience, saves, and private trip references unchanged. Source links retain the external provider's own access controls. Files use the existing private `TRAVEL_ANGELS_TRIP_MEDIA_BUCKET` under `trip-documents/*`; grant the API role `s3:GetObject`, `s3:PutObject`, and `s3:DeleteObject` for this prefix. Original files are served through authenticated trip endpoints with fresh permission checks and no permanent S3 URL.

Attachments and comments include their contributor's display name. Authors can remove their attachments, edit or remove their comments, and hosts can moderate by removing either. Each trip allows 100 attachments; each document allows 1,000 comments with pages of up to 100. Attachment APIs live under `/travel-angels/calendar/stops/:id/documents`, with `/upload`, `/:documentId/file`, and `/:documentId/comments` routes. Apply migration 481 and the storage prefix permission before deploying the updated API and Flutter clients. Rolling migration 481 down removes attachment/comment records, so do not use it as an ordinary code rollback.

**Flight lookup and traveling together.** Migration `000480_travel_flight_selections` adds personal flight selections independently of host-editable trip content. Hosts can look up a flight by number and departure date or by departure airport, arrival airport, and date. The lookup fills the existing editable flight legs, including each airport's local date, time, and IANA time zone. Manual entry remains available when schedules are unpublished, the provider is unavailable, or no API key is configured. FlightAware schedule access and geographic/date coverage depend on the account's entitlement and the airline's published schedule; the application does not infer live seat availability or fares from schedule results.

Configure a FlightAware AeroAPI account with schedule and airport lookup access. For the aggregated production API, store its key as the plain value of an existing AWS Secrets Manager secret and set Terraform's optional `flightaware_api_key_secret_arn` to that secret's full ARN. `terraform/travel_flights.tf` and `terraform/ecs.tf` inject `FLIGHTAWARE_API_KEY` into the core container and permit the task execution role to read only that configured secret. Leaving the ARN empty adds no secret dependency and keeps lookup disabled; Terraform does not create or overwrite an empty credential. Standalone/local servers can read the same environment variable directly.

Published flight cards support self-reported `considering` and `booked` selections for all or selected legs. Guests may browse flights permitted by the trip and flight audiences; claiming an account does not submit a flight choice or RSVP. A claimed trip host or currently confirmed attendee can save a choice. Each traveler edits only their own selection. Joining a flight in Travel Angels never buys a ticket, changes a reservation, or consumes another trip place. The external search action uses the host's flight link when supplied and otherwise opens a search for the itinerary; it does not promise an exact bookable offer. No confirmation numbers or ticket identifiers are collected.

Sharing a flight selection is opt-in and follows the trip's roster audience: hosts only, or hosts and confirmed attendees who can read the flight. When that audience changes, existing trip roster consent must be renewed before sharing again. Personal choices are excluded from the hosts' trip activity log. Private host assignments are separate and never become the shared flight roster. Flight selections survive draft edits and publication. A material change to a selected leg requires explicit reconfirmation; simple itinerary reordering and edits to other legs do not move or overwrite a traveler's choice. Cancellation prevents new selections while allowing existing choices to be removed. Removed flights and revoked trip/flight access are no longer readable. Older manually entered legs receive stable identifiers when read, so existing itineraries remain editable.

Flight lookup is `GET /travel-angels/calendar/stops/:id/flight-search`. Published, authorized selection state is `GET /travel-angels/calendar/stops/:id/flights/:flightId/travelers`, which includes the reviewed flight snapshot and its version. `POST /travel-angels/calendar/stops/:id/flights/:flightId/selection` saves or removes the caller's choice with that version and selected leg IDs. Selection writes do not write the host's draft or publish the trip.

**Trip destinations.** Migration `000477_travel_destinations` adds a canonical destination catalog, indexed search terms, and private per-user selection history. It seeds 249 countries and territories, so country autocomplete works without an external lookup. The authenticated `GET /travel-angels/destinations?q=...` endpoint searches names and aliases and ranks the caller's recently/frequently selected places. New places can be resolved through the existing Google Maps client (`GOOGLE_MAPS_API_KEY`); provider failures leave the local catalog available. Country relationships use structured provider data, and ambiguous regions do not imply a time zone.

Trips accept an ordered `destinations` array of up to 12 canonical IDs or custom names. IDs resolve to server-controlled snapshots stored independently in draft and published content. Custom names stay local to the trip and never enter the shared catalog. The legacy `destination` summary remains available to older clients, and existing free-text destinations are preserved as one location rather than split or guessed. Unrelated edits from older clients preserve structured locations. Changing selected places or their order requires the same attendance reconfirmation as other material trip changes. Place metadata and theme fields provide a foundation for later destination styling; destination pages, automatic styling, and per-location dates are not part of this release.

Stop content is drafted before publication, while confirmed sharing changes apply immediately. Access changes preview affected participation. Revoking a person's last access path removes their active participation and pauses updates. Link rotation checks the actual links previously used by participants/subscribers; it does not grant access through an alternative link they never received. Dates remain local `YYYY-MM-DD` values. A destination IANA time zone, defaulting explicitly to UTC, determines when a stop has ended.

**Verification.** From the Flutter package, run `flutter test` and `flutter build web --no-pub`. From `go/travel-angels`, run `go test ./...`. Database integration tests are included in `internal/travelcalendar`; set `TC_TEST_DATABASE_URL` to a disposable PostgreSQL database to run them. Each integration test creates a unique schema, loads the actual migrations, uses a fake mail sender, and removes that schema afterward. The supplied database role needs schema-creation permission. Coverage includes publication, permission replacement, account claiming, partial dates, reconfirmation, capacity, host roles, revocation/rotation, protected media, logistics visibility, delivery retries, and migration rollback/reapplication.

**Release.** Apply repository migrations through 481, provision the private trip-media bucket and role permissions (`trip-heroes/*`, `trip-lodging/*`, and `trip-documents/*`), and configure `TRAVEL_ANGELS_TRIP_MEDIA_BUCKET` before rolling out the API that serves Travel Angels (the aggregated core service or standalone Travel Angels service, depending on the environment). Production uses the `core` image in the `sonar_core` ECS service. Configure the optional FlightAware secret to enable flight lookup, then release the rebuilt Flutter web/iOS clients. Existing trip links, calendar references, and previously uploaded covers remain valid. Destination/property lookup uses the existing Google Maps key and uploaded image storage uses the existing AWS client. Property lookup additionally needs Places API (New) enabled. Migration 480 rollback deletes saved personal flight selections; downgrade the client/API before rolling it back.

Public web hosting and the URL-only runtime update have separate deployment workflows described above. Web deployment does not run production migrations or send invitations. Calendar access, email delivery, and existing phone authentication must be configured in the environment where the feature is deployed.
